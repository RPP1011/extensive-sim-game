# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with this repository.

## What this crate is

`engine_data` holds the shared game-data vocabulary that `crates/engine` compiles against but must not itself define, per the "engine contains zero game logic" rule (`docs/game/overview.md`). It was originally meant to be 100% `dsl_compiler` output (see Provenance below — that is no longer true in practice). Modules:

- `entities/` — `CreatureType` enum (Human/Wolf/Deer/Dragon), the hostility matrix (`is_hostile_to`), and `Capabilities` (per-creature-type struct: comm channels, languages, can_fly/can_build/can_trade/can_climb/can_tunnel/can_marry, herding behavior).
- `types.rs` — `ChannelSet` / `CommunicationChannel` / `LanguageId`, moved here from `engine::channel` / `engine::creature` at Milestone 6 so compiler-emitted `Capabilities` doesn't force `engine_data → engine` to invert.
- `events/` — one file per event struct (`AgentDied`, `EffectDamageApplied`, ...) plus `events::Event`, the tagged-union enum aggregating all of them (with `tick()` / `is_replayable()`).
- `enums.rs` (dir) — small standalone enums referenced by event fields (`CombustionReason`, `GroupBehavior`), plus `QuestCategory` / `Resolution` in `types.rs`.
- `config/` — one struct per DSL `config` block (`CombatConfig`, `MovementConfig`, `NeedsConfig`, `CommunicationConfig`, `BeliefConfig`), aggregated into `Config`, loadable via `Config::from_toml`.
- `scoring/` — POD `ScoringEntry`/`ModifierRow`/`PredicateDescriptor` table (`SCORING_TABLE`), one row per `MicroKind` action head; CPU-scorer- and future-GPU-buffer-compatible (`#[repr(C)]`).
- `schema.rs` — the `*_HASH` constants (`STATE_HASH`, `EVENT_HASH`, `RULES_HASH`, `SCORING_HASH`, `CONFIG_HASH`, `ENUMS_HASH`, `VIEW_HASH`, `GPU_RULES_HASH`, `COMBINED_HASH`) that `engine`'s `schema_hash.rs` test validates against.
- `ids.rs` — transitional `NonZeroU32` newtypes (`AgentId`, `GroupId`, `ItemId`, `QuestId`, `AuctionId`, `InviteId`, `SettlementId`, `AbilityId`, `EventId`). Explicitly transitional: the doc comment says the canonical path is meant to become `engine::ids::*` once the `engine_data → engine` dep direction inverts (Plan B1' Task 5/6); until then `engine::ids` re-exports from here.
- `id_serde.rs` — hand-written serde glue (niche IDs serialize as plain `u32`).
- `belief.rs` — `BeliefState` (Theory-of-Mind per-(observer, target) fact tuple), hand-written because `SimState` itself is hand-written in `engine` (same deviation noted in ToM Task 3).

`engine` depends on `engine_data` (see `crates/engine/Cargo.toml`), currently **only** for `chronicle.rs` — that comment says the dep is retained "ONLY for chronicle.rs until Plan B2 migrates chronicle to emitted DSL (Spec B' §4.2); drop this line in Task B2." Don't assume other `engine` modules should reach into `engine_data`; `creature.rs`, `channel.rs`, `mask.rs`, `ids.rs` etc. are re-export shims left over from the Milestone-6/Task-4 migration, not new coupling points.

## Build & test

```bash
cargo build -p engine_data
cargo test -p engine_data
cargo test -p engine_data -- agent_id_roundtrip_and_ordering   # single test
```

There is effectively one test module in this crate today: `src/ids.rs`'s `#[cfg(test)] mod tests`. Everything else is data with no logic to unit-test directly (it's exercised indirectly via `engine`/`sims` fixture pin tests).

## Architecture: CreatureType + Capabilities

`entities/mod.rs` defines `CreatureType` (the 4-variant enum + `ALL` + `name()` + `is_hostile_to`) and `Capabilities::for_creature(CreatureType) -> Capabilities` (one big `match` with a literal struct per variant). The four sibling files `entities/{human,wolf,deer,dragon}.rs` are **intentionally near-empty** — each is just a `pub(super) const __ENTITY_<NAME>: &str` marker plus a comment pointing back at `mod.rs`, which is where the actual `CreatureType` variant, hostility-matrix arm, and `Capabilities::for_creature` arm for that creature all live. Don't expect per-creature logic split across files the way the directory layout suggests — all four creatures' behavior is centralized in `mod.rs`.

## Provenance of the `// GENERATED` files — verified, not assumed

This is the load-bearing finding for any follow-up work on trimming wolf/human/deer/dragon coupling out of the engine layer:

**There is no live codegen path for this crate today.** `crates/engine_data/build.rs` is a *sentinel*, not a generator — its own doc comment calls it that. It does exactly one thing: walk `src/`, and for every `.rs` file not on a small top-level allowlist (`lib.rs`, `ids.rs`, `types.rs`, `id_serde.rs`, `belief.rs`), panic unless the file's first 5 lines contain the literal string `// GENERATED by dsl_compiler`. It never invokes `dsl_compiler`, never reads any `assets/sim/*.sim` file, and never writes to `OUT_DIR` or back into `src/`. Contrast this with, e.g., `crates/sims/build.rs`, which really does compile `.sim` sources at build time.

Every `// GENERATED` file also carries a second header line: `// Was regenerated by xtask 'compile-dsl'; xtask retired in Phase 7 (2026-05-02), file now hand-maintained.` (entity files phrase it as `// Was emitted from .sim source by xtask 'compile-dsl' (retired Phase 7, 2026-05-02); now hand-maintained.`). That comment is accurate, and independently verifiable: the `.sim` source files these headers cite by name — `assets/sim/entities.sim`, `assets/sim/enums.sim`, `assets/sim/events.sim`, `assets/sim/config.sim` — **do not exist anywhere in the repo** (`assets/sim/` today holds ~100 fixture `.sim` files like `predator_prey.sim`, `boids.sim`, `duel_1v1.sim`, none named `entities.sim`/`enums.sim`/`events.sim`/`config.sim`). So the header isn't just stale about the *mechanism* (xtask retired) — the *source of truth it names* is gone too. There is nothing left to regenerate these files from even if you wanted to.

So: `// GENERATED by dsl_compiler` in this crate is a **misleading historical header**, kept alive only because the pre-commit hook (`.githooks/pre-commit`, Spec B' §7) still hard-requires it on any staged `crates/engine_data/src/**/*.rs` file outside the tiny allowlist, and requires its *absence* everywhere else in the repo. In practice this crate today is 100% hand-maintained; the header is a frozen snapshot of what `dsl_compiler` once emitted at Milestones 1/4/5/6/13 (see `docs/game/compiler_progress.md`), preserved because the tooling that enforces the header format doesn't know the milestones that produced it are gone. `crates/dsl_compiler` itself is alive and still used elsewhere (e.g. `crates/sims/build.rs` compiles fixture `.sim` files into `sims::<fixture>::GeneratedRuntime` at real build time) — it's specifically the engine_data-targeting emission pass that has no live invocation anymore.

Practical implications for a coupling-trimming task:
- Editing `entities/mod.rs` (or any other `// GENERATED` file here) by hand is the *normal* way to change it now — there's no `.sim` source to edit instead and no regeneration step to run afterward. Just keep the header intact (or the pre-commit hook's header-presence check fails) and don't touch it if you move code elsewhere.
- If wolf/human/deer/dragon-specific data moves out of `engine_data` (e.g. into a game-content crate one layer up), the four-fixed-variant `CreatureType`/`Capabilities` shape is not compiler-enforced or regeneration-enforced — it's just what's hand-written today. Nothing will "regenerate it back."
- `.githooks/pre-commit`'s allowlist for the header-exemption still lists only `ids.rs` / `types.rs` / `id_serde.rs` — it has not been updated for `belief.rs`, which `build.rs`'s allowlist *does* include (added later, per Plan ToM Task 3). If you add `belief.rs`-like hand-written files going forward, update `HAND_WRITTEN_ALLOWLIST` in `build.rs` *and* the corresponding `case` arm in `.githooks/pre-commit`, or commits touching such a file will be blocked by a hook that doesn't know about it.

## Other non-obvious things

- `schema.rs`'s hash constants are static byte arrays, not computed at build time in this crate — nothing here hashes anything; `engine::schema_hash` (or the equivalent runtime test) is what reads and validates against them.
- `scoring::SCORING_TABLE` predicate rows are hand-encoded POD (`PredicateDescriptor` with a raw `payload: [u8; 12]`, little-endian-packed thresholds/arg-slot codes) — e.g. `EffectDamageApplied`'s `Attack` head modifiers encode view-call args and belief-field indices directly into byte payloads. There's no higher-level DSL expression type left in this crate to decode them from; the encoding scheme is documented only in the doc comments on `PredicateDescriptor`'s `KIND_*`/`ARG_*`/`BELIEF_FIELD_*`/`VIEW_ID_*`/`OP_*` constants (cross-reference `docs/dsl/scoring_fields.md` if editing by hand).
- `ids.rs` is explicitly transitional (see its module doc): the struct bodies live here today only because `engine::ids` hasn't yet become the canonical home; don't add new ID newtypes assuming this is the permanent location.
- `types.rs`'s module doc records that `engine::channel` / `engine::creature` re-export from here specifically so old `engine::` import paths keep compiling — if you're chasing down why `CommunicationChannel` seems to be defined in two places, this is why (one is a re-export shim).
