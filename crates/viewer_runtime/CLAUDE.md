# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with this repository.

## What this crate does

`viewer_runtime` is a windowed **presentation** layer, not a sim. It owns no gameplay rules — it drives a `sims::*` `GeneratedRuntime` (compiled from a `.sim` DSL file), reads the GPU agent SoA back to host each tick, and paints what it reads into a CPU `VoxelGrid` that it re-uploads to a Vulkan texture every frame for `voxel_engine`'s `VoxelRenderer::render_frame_gpu` to draw. It also drives an optional glTF-character mesh overlay pass on top of the voxel splats.

Two GPU contexts exist side by side and never share state directly: `state.gpu` (wgpu) drives the sim's compute kernels; the renderer (`voxel_engine`) owns a separate Vulkan instance/device created in the `bin/*.rs` entry point. The bridge crosses that boundary by reading sim buffers back to a host `Vec` and re-uploading them into the renderer's texture — cheap at the grid sizes used here (96×96×~12–20 cells).

**There are two independent pilot fixtures in this one crate**, despite the Cargo.toml header comment only mentioning the first:

- **`dungeon_horde`** (`src/dungeon.rs`, `bin/viewer_app.rs`) — 5 heroes vs. ~200-1000 enemies in a hand-laid 21-room voxel dungeon. This is the older/primary pilot and the one with the most machinery (fog of war, boss fight, per-role hero AI, damage/heal flashes, projectile VFX, HP bars).
- **`vampire_survivors`** (`src/vs.rs`, `src/vs_ui.rs`, `bin/vs_viewer.rs`, `examples/vs_capture.rs`) — a single player vs. a drained/pooled enemy horde in a flat 96×96 arena, with an `engine_ui`-driven HUD/level-up/death-screen overlay (`vs_ui.rs`). Voxel splats only — no mesh overlay (`vs_viewer.rs`'s header comment explains why: VS roles don't map to the dungeon creature-type mesh slots).

Both follow the same shape: a `*ViewerApp` (or `VsViewerApp`) owning the `GeneratedRuntime` + host-side per-agent cache, and a `*Bridge` (`VoxelBridge` / `VsBridge`) that paints that cache into a `VoxelGrid` and manages the `GpuVoxelTexture`. `VsBridge` lives in `vs.rs`, not `lib.rs`.

### `dungeon.rs`

Pure-CPU dungeon construction, deliberately **not** shared code with the pin test it mirrors. It hand-lays a 21-room layout (`ROOM_LAYOUT`, a fixed array of `(rx, ry, RoomTemplate)`), computes per-room BFS distance from spawn, derives enemy composition/counts per room (density formulas tuned for "watchable" combat, not gameplay balance), and stamps per-template wall patterns (`Open`/`Pillared`/`Partition`/`Treasure`/`Boss`). Its module doc explicitly says it's "load-bearing copy-paste" from `crates/sims/tests/dungeon_horde_pin.rs` — the pin keeps its own CA-based roomgen and the two are decoupled on purpose so viewer layout can be iterated without touching the pinned test fixture. **Do not try to unify them without reading both first** — drift is intentional, but only within known bounds (see below).

`seed_voxel_dungeon` and `seed_topology` are the two functions that actually write to the GPU (`state.gpu.queue.write_buffer(...)` for terrain cells and agent SoA fields respectively). Everything else in the module (BFS, room templates, `pick_next_target`/`pick_retreat_target` frontier-greedy room selection, `door_position`) is pure CPU math ported from the pin's host-side hero-exploration helpers.

### `mesh_renderer.rs`

Two responsibilities in one file: `MeshCpu::load_glb` (glTF loading via the `gltf` crate — first mesh/primitive only, positions+normals+colors+optional skinning, documented as "Phase 1 — loading only" though the Vulkan overlay pipeline described below is now also implemented in the same file), and `MeshRendererGpu` (the actual Vulkan pipeline: `add_mesh` uploads a `MeshCpu` to GPU buffers and returns a mesh-slot index; `record_overlay` records an instanced draw per `MeshDraw{mesh_slot, instances}` bucket into the swapchain's blit-with-overlay command buffer). `InstanceData::from_pos_facing` packs a world position, uniform scale, XZ-plane facing vector, and RGB tint into the per-instance record consumed by `shaders/mesh.vert`/`mesh.frag` (precompiled `.spv` checked in alongside the `.glsl`-equivalent source — there's no `voxel_engine`-style freshness-check build step here, so if you edit the `.vert`/`.frag` you must recompile the `.spv` by hand and commit both).

### `bin/viewer_app.rs`

The dungeon_horde windowed binary. `cargo run -p viewer_runtime --bin viewer_app --release [SEED]` (hex `0x...` or decimal; defaults to `0xD007_BEEF_5_7EA1`, the same seed `dungeon_horde_pin` pins). Opens a winit window, drives a `WindowedViewer: ApplicationHandler` at a fixed 50ms sim-tick cadence (independent of frame rate — `RedrawRequested` catches up on however many ticks have elapsed, capped at 8/frame), interpolates agent positions between ticks for smooth motion, buckets alive agents into 11 mesh slots (5 hero roles + 2 variants × 3 enemy types) for the mesh overlay pass, and ray-casts a coarse per-agent wall-occlusion check before drawing each mesh instance. It **auto-restarts with the next seed** ~3 seconds after a run terminates (TPK or dungeon cleared) — it is meant to run unattended as a continuous demo reel, not as a one-shot viewer. Controls: Space pauses/resumes, R force-restarts on the next seed immediately, WASD/arrows pan, +/- zoom.

### Tests

- `tests/smoke.rs` — headless (no window/Vulkan), constructs `ViewerApp`, asserts agent counts and hero-alive count at construction, steps 5 ticks, asserts no NaN positions. Skips silently (not a failure) if no wgpu adapter is present on the host — **CI/headless machines without a GPU will show this test as skipped, not run**.
- `tests/diag_hero_movement.rs` (`diag_hero_movement_under_full_viewer_loop`) — drives the *full* `ViewerApp::step` loop (sim step + `advance_hero_exploration` + `refresh_snapshot`, same order as production) for 400 ticks and asserts each hero's cumulative path length exceeds a floor of 30 units. This is a regression guard for a specific historical bug (heroes freezing at a door midpoint because `HeroExplore`'s `dist > 0.5` cutoff fired before crossing it) — read the test's trailing comment before touching hero waypoint/retreat logic.
- `tests/smoke_vs.rs` — the vampire_survivors equivalent: constructs `VsViewerApp`, asserts exactly 1 player and 0 enemies before any wave, steps 60 ticks, asserts enemies eventually spawn and positions stay finite; also headlessly exercises `vs_ui`'s HUD/level-up/death-screen `egui` draw calls with no GPU/display needed.

Run with `cargo test -p viewer_runtime`. Build with `cargo build -p viewer_runtime` (or `--release` — the binaries are unusable at debug-build frame rates given the per-tick GPU readback).

### On "hero" — precise answer for engine/game-content cleanup

`Hero` is **not** a generic test-fixture name here — it is real, load-bearing game content specific to the `dungeon_horde` sim. `dungeon::CT_HERO` is one of four creature-type constants the `.sim` DSL itself defines (`assets/sim/dungeon_horde.sim`, alongside archer/brute/goblin), and role `1..=5` maps to five named hero classes (Warrior/Cleric/Ranger/Mage/Rogue) with per-role AI behavior (`advance_hero_exploration` in `lib.rs`), per-role mesh assignments, and per-role palette colors baked throughout `lib.rs`, `dungeon.rs`, and `bin/viewer_app.rs`. `diag_hero_movement.rs`'s "hero" refers to these five specific agents, not a placeholder. Anyone doing an engine-vs-game-content split should treat essentially all of `dungeon.rs`, the hero-exploration AI in `lib.rs`, and the dungeon-specific material palette (`MAT_HERO_BASE`, `MAT_BOSS`, etc.) as **game-specific**, not engine — this whole crate is a per-fixture viewer binary in the "one-crate-per-fixture" pattern the workspace root CLAUDE.md flags for eventual retirement, and `dungeon_horde` is a real gameplay concept baked into it, not a stand-in.

## Architecture: SoA → voxel grid → renderer, end to end

1. `sims::dungeon_horde::GeneratedRuntime` (or `vampire_survivors`) holds agent state as GPU storage buffers — one buffer per field (`agent_pos_buf`, `agent_hp_buf`, `agent_alive_buf`, `agent_creature_type_buf`, `agent_alert_buf`, `agent_target_room_idx_buf`, etc.), the standard SoA layout the `.sim` DSL compiler emits.
2. Each tick, `ViewerApp::step` calls `state.step()` (advances the sim's GPU compute kernels), then `refresh_snapshot` reads every relevant buffer back to host via `read_positions`/`read_agent_u32`/`read_agent_f32` — each spins up a `COPY_DST | MAP_READ` staging buffer, `copy_buffer_to_buffer`, `map_async` + blocking `device.poll(PollType::Wait)`. This is a **synchronous, blocking readback every tick** — fine for a demo viewer at ~1000 agents, but not a pattern to reuse in anything latency-sensitive.
3. The host cache (`Vec<AgentSnapshot>`) is diffed against the previous tick's cache to derive events with no dedicated sim signal: damage/heal flashes (HP delta ≥ threshold), death-fade start, nearest-opposite-team projectile source, per-room "cleared" state, fog-of-war knowledge bitmaps, facing direction (low-pass-filtered position delta). None of this is sim state — it's all host-side inference from position/HP/alive deltas.
4. `VoxelBridge::refresh` paints the diffed state into a CPU `VoxelGrid` (`voxel_engine::voxel::grid::VoxelGrid`) — floor/wall cells from `dungeon.floor_cells` (static, seeded once), agent splats/shadows/HP-bars/projectile beams repainted every frame from `last_agent_cells` (cells painted last frame are restored to floor/air before repainting, so the agent layer stays sparse). The grid is then destroyed and fully re-uploaded to GPU (`upload_grid_to_gpu`) every frame — needed because `voxel_engine`'s renderer relies on a mip chain for empty-space skipping, and a partial update wouldn't regenerate it.
5. `bin/viewer_app.rs`'s render loop calls `renderer.render_frame_gpu(&ctx, &camera, &[bridge.render_object()])` for the voxel layer, then separately buckets alive agents by mesh slot and calls `mesh.record_overlay(...)` inside `swapchain.present_blit_with_overlay`'s callback to composite character meshes on top.

A world-space **axis swap** runs through the whole bridge: the sim is Z-up (`agent.pos = (x, y, z)`, Z is vertical), `voxel_engine`/the renderer is Y-up, so every place sim coordinates cross into renderer/grid space does `(x, y, z) → (x, z, y)`. This is not commented at one central place — it's repeated inline at each site (`VoxelBridge::refresh`, the mesh-instance loop in `viewer_app.rs`, `agent_occluded_by_wall`). If you add a new sim-space value that needs to reach the renderer, apply the same swap.

## Non-obvious gotchas

- **HP overrides at construction are demo tuning, not sim balance.** `ViewerApp::try_new` overwrites `agent_hp_buf`/`agent_max_hp_buf` after `seed_topology` runs (archer=22, brute=45, goblin=15, boss=400, hero stays at the `.sim`'s 200 default) purely so a 5v~1000 fight resolves in ~30–60s wall clock instead of ~3 minutes. Don't read these as authoritative combat numbers.
- **The "boss" is not a sim concept.** It's the first Brute the viewer happens to place inside the boss room (`seed_topology`'s return value), given 400 HP and a distinct color/mesh scale purely by the viewer. `maybe_enrage_boss_room` bumps every boss-room enemy's `alert` field once the boss crosses 50% HP — this is a one-shot host-authored gameplay beat, not something the `.sim` DSL expresses.
- **Two independently-evolving "hero AI"s exist**: the `.sim`'s own `HeroExplore` GPU rule, and `ViewerApp::advance_hero_exploration` (host-side, CPU, runs every tick before `refresh_snapshot`) which overwrites `agent_target_room_idx_buf` and the waypoint buffers with a richer per-role policy (warrior leads via frontier-greedy, cleric chases the lowest-HP wounded teammate, rogue scouts one room ahead, low-HP heroes retreat with hysteresis, a "boss-push" override kicks in past 60% kills). The GPU-side rule and the host override run every tick; the host override's writes are the ones that actually stick within a tick since they happen after `state.step()`.
- **`voxel_engine` is pulled from git at a pinned rev** (not a published crate, not a path dep to a local sibling checkout) with `features = ["app-harness"]` layered on top of `engine_voxel`'s default-feature dependency on the same git rev — Cargo unifies these into one build only because the `git`+`rev` coordinates match exactly. If you bump the rev here, check `engine_voxel`'s Cargo.toml for the same rev or you'll get two copies of the crate and type-identity failures across the crate boundary (e.g. `VoxelGrid` from one `voxel_engine` isn't the same type as `VoxelGrid` from the other).
- **`wgpu` is pinned to `=26.0.1`** (exact, not `^`) — it's used only for the sim-side readback, but an exact pin means a routine `cargo update` will not move it; bump deliberately.
- **The mesh pack is a runtime asset dependency, not a build dependency.** `assets/models/kenney_mini-characters/Models/GLB format/*.glb` is loaded from a relative path at startup; if missing, `MeshCpu::load_glb` fails and is logged but not fatal — the viewer falls back to voxel-splat-only agents. Don't assume mesh presence when testing.
