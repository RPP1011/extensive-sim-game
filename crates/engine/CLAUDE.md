# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with this repository.

## What this crate is

`engine` is the primitives library the DSL compiler and per-fixture runtime crates target — SoA agent state, spatial hash, event ring, RNG, mask buffer, cascade dispatch, view traits, snapshot/save-load, schema hashing, observation packer, telemetry, and the sim-agnostic GPU platform layer (`engine::gpu`: `GpuContext`, `Kernel` trait, BGL helpers). Per `docs/game/overview.md`'s hard rule, engine contains **zero game logic** — see the wolf-sim-coupling findings below for the two places that rule is currently bent. Root `CLAUDE.md` already covers the `ComputeBackend` trait's role as the CPU/GPU split point and the `per_agent_u32` determinism rule; this file doesn't repeat those.

**Important reality check for anyone reading `step.rs`, `backend.rs`, `scratch.rs`, or `probe/mod.rs`:** these are *not* live tick-orchestration code today. Plan B1' Task 11 deleted the real `step`/`step_full` implementations; `step.rs` is now `unimplemented!()` compile-only stubs kept so old `#[ignore]`d tests still import cleanly. The doc comments across the crate point at `engine_rules::step` as the future canonical driver, but `engine_rules` was one of the crates deleted in the Phase 7 wolf-sim wipe (2026-05-02, see root `Cargo.toml` comment) and has not been recreated — it is not a workspace member today. `benches/tick_throughput.rs` still calls `engine::step::step` and will panic at runtime if executed; treat it as stale pending the Task 11 cleanup, not as a working benchmark. `probe::run_probe` is similarly unimplemented pending the same task.

The actual current tick driver for a real fixture is compiler-emitted per fixture (`crates/dsl_compiler/src/cg/emit`), living inside `crates/sims`' generated `GeneratedRuntime` modules or a legacy `crates/*_runtime` crate (e.g. `tom_probe_runtime`). Those implement `engine::sim_trait::CompiledSim` and call engine primitives (`Pool`, `EventRing`, `CascadeRegistry`, `MaskBuffer`, spatial index, ability registry) directly — not through `engine::step` or `ComputeBackend`. `ComputeBackend` (backend.rs) exists as a trait shape but has zero concrete implementations anywhere in the workspace today (`grep -rl "impl.*ComputeBackend"` under `crates/` is empty) — treat it as forward-looking scaffolding, not a live abstraction boundary you can rely on being exercised.

## Commands specific to this crate

```bash
cargo build -p engine
cargo test -p engine                       # crate's own tests/*.rs (69 files)
cargo test -p engine <test_fn_or_module>    # single test / filtered by name
cargo test -p engine --test <file_stem>     # one integration-test binary, e.g. --test spatial_index
cargo test -p engine --features interpreted-rules   # parity gate: DSL-IR-interpreted path must match the compiled path's replayable_sha256 byte-for-byte
cargo test -p engine --release              # release-mode variants of proptests/acceptance tests that are slow in debug
cargo bench -p engine                       # [[bench]] tick_throughput — currently broken, see reality-check above
```

`no-contracts` feature elides `contracts::{invariant, requires, ensures}` attributes (useful when benchmarking without debug-build contract overhead). `dhat-heap` feature gates the `dhat` allocation-profiling tests (e.g. the zero-alloc-per-tick budget checks noted in `docs/engine/status.md`'s weak-test-risk #9). `theory-of-mind` gates the belief subsystem (cold field + cascade rules), zero cost when off.

## Structural guardrails (crate-specific, beyond the workspace pre-commit hook)

`build.rs` enforces two rules on `src/` at every build, independent of the pre-commit hook the root `CLAUDE.md` mentions:

1. **Allowlist.** Every top-level file and directory under `src/` must appear in `build.rs`'s `ALLOWED_TOP_LEVEL` / `ALLOWED_DIRS` constants. Adding a new primitive requires editing that list *and* is a constitutional governance event (Spec B' §5 D11: pros/cons writeup + 2 biased-against critic PASSes + user approval recorded as an ADR) — this is stricter than an ordinary code change.
2. **No `// GENERATED by dsl_compiler` marker anywhere under `src/`**, except the single carve-out `event/event_like_impl.rs` (a Task 2 workaround for `impl EventLike for engine_data::events::Event`, pending a Task 5 follow-up that moves it to `engine_data`). Generated code belongs in `engine_data` or a per-fixture runtime crate, never in `engine` itself.

Both violations panic the build with an explanatory message. If you're about to add a new top-level module or paste in compiler output, read `build.rs` first.

## Internal architecture (requires reading multiple files to see)

- **State + identity**: `state/` (`SimState`, hot/cold SoA split per `docs/spec/state.md`), `pool/` (`Pool<T>`/`PoolId<T>`, `NonZeroU32`-niched, freelist reuse — `ids.rs` builds `AgentId` etc. on top), `spatial.rs` (2D-column `BTreeMap` + z-sort + `MovementMode` sidecar, 16m grid). These compose as: agents live in `state`'s SoA vectors indexed by slots `pool` hands out; `spatial` maintains its own index keyed by the same ids, rebuilt/patched alongside spawn/kill/move.
- **Events + cascade**: `event/` declares `EventLike` + `EventRing<E>` (the type itself is generic — `engine_data::events::Event` is the concrete vocabulary, wired in via the one generated-marker exemption above). `cascade/` (`dispatch.rs` + `handler.rs`) provides `CascadeRegistry<E, Views>`, `CascadeHandler`, and `Lane` ordering (Validation → Effect → Reaction → Audit); `run_fixed_point` bounds cascade iteration at `MAX_CASCADE_ITERATIONS = 8`. A per-fixture runtime wires its own compiler-emitted handlers into a `CascadeRegistry` and drives dispatch itself (see "reality check" above — this is not orchestrated by anything in `engine` today).
- **Action selection**: `mask.rs` (`MaskBuffer`, 18-bit-per-agent head covering `MicroKind`) and `policy/` (`PolicyBackend` trait, `UtilityBackend` scalar scorer, `macro_kind.rs`, `query.rs`) are primitives only — the actual predicate/scoring bodies are compiler-emitted per fixture, not hand-written here (see `docs/game/compiler_progress.md` milestones 3–4, "done").
- **Views**: `view/` — `MaterializedView` (per-tick fold), `LazyView` (staleness-tracked, computed on demand), `TopKView` (bounded per-entity heap). Three storage strategies, one trait family; a fixture's generated views implement whichever trait matches its `.sim` `@materialized`/`@lazy`/topk declaration.
- **RNG**: `rng.rs` — `WorldRng`, PCG-XSH-RR. All draws must route through `per_agent_u32` (root `CLAUDE.md` P5); this crate only provides the generator, not the call-site discipline.
- **GPU platform split**: `gpu/` is intentionally *sim-agnostic* — `GpuContext` (wgpu device/queue), `Kernel` trait, BGL-entry helpers (`bgl_storage`/`bgl_uniform`). Engine carries the (heavy) `wgpu` dependency so per-fixture runtime crates don't each redeclare it; the actual compute kernels and dispatch modules are compiler-emitted per fixture and `impl engine::gpu::Kernel` against this surface. Engine knows nothing about what a kernel computes.
- **Integration contract**: `sim_trait.rs`'s `CompiledSim` — not `ComputeBackend` — is the trait a per-fixture runtime crate actually implements today, and what `sim_app` depends on to stay fixture-agnostic (swap fixtures via a Cargo alias, not a code change).
- **Schema hash**: `schema_hash.rs` computes a SHA-256 fingerprint over a hand-maintained string literal describing every layout-relevant type (SoA field list, `Event` variant list, `MicroKind`, `CreatureType`, ability/effect vocabulary, tuning constants...). `crates/engine/.schema_hash` pins the baseline; `tests/schema_hash.rs` fails CI on drift. Because the string is hand-written, it silently under- or over-covers reality — status.md's weak-test-risk table already flags this (nothing proves e.g. `ItemId` size flows into the hash). When you change a layout type, update the literal *and* the baseline file in the same commit.
- **Snapshot / save-load**: `snapshot/format.rs` + `migrate.rs` — binary discriminant-based encode/decode, `SnapshotError::InvalidDiscriminant` on unknown values.
- **Other primitives**: `aggregate/` (`AggregatePool<T>` for `Quest`/`Group`-shaped pooled aggregates), `invariant/` (`Invariant` trait, `InvariantRegistry`, `FailureMode::{Panic,Log}`, built-ins `MaskValidityInvariant`/`PoolNonOverlapInvariant`), `obs/` (observation packer + `FeatureSource` impls), `telemetry/` (`TelemetrySink` + `Null`/`Vec`/`File` sinks), `trajectory.rs` (safetensors trace emission), `debug/` (repro-bundle + agent-history tooling), `terrain.rs` (tiny `TerrainQuery` trait seam, `FlatPlane` default — `engine_voxel` supplies the real backend without engine depending on wgpu-adjacent voxel internals), `channel.rs` (communication-channel range dispatch table — a worked example of the split rule: balance numbers moved to `assets/sim/config.sim`, but the dispatch logic itself stays here because it's keyed on an engine enum, not a tunable).
- **`evaluator/`**: DSL IR interpreter context impls (`ReadContext`/`CascadeContext` over `SimState`), entirely gated behind the `interpreted-rules` feature — zero cost in the default build. Exists in `engine` rather than a rules crate specifically to avoid a circular dependency.

Spec cross-references (section numbers from `docs/spec/engine.md`, not restated here): §3–4 state/pool, §5 event ring, §6 spatial, §7 RNG, §9–10 mask/policy micro/macro kinds, §11 cascade, §12 mask buffer, §13 policy backend, §14 six-phase tick pipeline (contract only — no current implementation in this crate, see reality check), §15 views, §16 aggregates, §17 trajectory, §18 save/load + probes, §19 invariants, §20 schema hash, §21 obs packer, §22 telemetry, §23 debug/trace (not started), §24 `ComputeBackend`/backends (not started — see status.md). `docs/engine/status.md` has a per-subsystem table with the same § numbers, live ✅/⚠️/❌ status, and cited test files — check it before assuming any of the above is fully verified rather than just present.

## Wolf-sim coupling: what's actually still hardcoded in `crates/engine`

Root `Cargo.toml`'s comment says `engine` and `engine_data` are "coupled to the wolf-sim type set today (CreatureType, wolf-flavored Event variants)." Verified against current source:

**`engine_data` (not this crate) still owns the fixed 4-variant vocabulary.** `crates/engine_data/src/entities/mod.rs` defines `CreatureType` as a hand-maintained (not currently DSL-regenerated — `xtask compile-dsl` was retired in the Phase 7 wipe, so the file's header now reads "file now hand-maintained") `#[repr(u8)]` enum with exactly `Human = 0, Wolf = 1, Deer = 2, Dragon = 3`, plus a hardcoded pairwise `is_hostile_to` matrix and `Capabilities::for_creature` spawn-time defaults per species. This is the real "wolf-sim type set" the Cargo.toml comment refers to, and it is genuinely not generic yet.

**`crates/engine` itself treats `CreatureType` as an opaque field type almost everywhere** — `state/agent.rs` and `state/mod.rs` store `Option<CreatureType>` as a cold SoA column with a generic getter (`agent_creature_type`), and `debug/agent_history.rs` just threads it through for tooling. No hostility logic, capability logic, or creature-specific behavior lives in `crates/engine` — `creature.rs` itself is now a doc-comment-only stub (Milestone 6 / Task 4 moved that vocabulary and all re-export shims to `engine_data`; callers import `engine_data::entities::CreatureType` directly).

**Fixed (see current source — this section is now historical).** Two hardcoded couplings used to live here, both at serialization/fingerprint boundaries:

1. `src/schema_hash.rs` used to contain the literal `h.update(b"CreatureType:Human,Wolf,Deer,Dragon")`. It now builds that fragment from `engine_data::entities::CreatureType::ALL` + `.name()` at call time — byte-identical output today (no baseline bump), but it can no longer silently drift if `engine_data`'s vocabulary changes.
2. `src/snapshot/format.rs`'s `creature_from_disc` used to hand-match the u8-discriminant ↔ variant mapping. It now calls `engine_data::entities::CreatureType::from_disc(v)`, a new method living next to the enum itself (`Self::ALL.iter().find(|ct| *ct as u8 == v)`) — same reasoning as `movement_mode_disc`/`movement_mode_from_disc` a few lines above, just not yet extended to `MovementMode` (that enum is engine-owned, not `engine_data`-owned, so it isn't part of this particular coupling).

Both changes were behavior-neutral: `cargo test -p engine -p engine_data` passes (`schema_hash_matches_baseline`, `schema_hash_is_stable`, all three `snapshot_roundtrip` tests) with no `.schema_hash` baseline edit needed.

Everything else the `Wolf|Human|Deer|Dragon` grep turns up (`ability/mod.rs`, `evaluator/mod.rs`, `policy/utility.rs`, `spatial.rs`, `state/mod.rs`, `terrain.rs`, `debug/repro_bundle.rs`) is a doc comment referencing "wolves+humans" as the historical parity-fixture name (`docs/game/wolves_and_humans.md`), not executable coupling.

**Remaining front (not fixed, and not attempted here):** `engine_data::entities::CreatureType` is still a fixed, hand-maintained 4-species enum, not a generic DSL-emitted one — there's no live `.sim` source or regeneration path for it (see `engine_data`'s CLAUDE.md, "Provenance"). Making it truly open-ended would mean reviving DSL-driven entity codegen, which is a much larger undertaking than delegation; that's out of scope for the delegation fix above and would need its own plan.
