# Playable Vampire Survivors — Plan Index & Parallelization DAG

> Spec: `docs/superpowers/specs/2026-05-25-interactive-runtime-playable-vs-design.md`.
> This index decomposes the spec into **five independently-landable plans** structured for **parallel execution**. Each plan is its own file with its own AIS preamble (P8) and TDD task list. Execute by wave; within a wave, dispatch one agent per plan.

## Implementation deviation from the spec (read first)

The spec proposed a new `input {}` block. Exploration found the DSL **already has** the `@runtime` config-field annotation (`ConfigField.runtime: bool`, parsed at `crates/dsl_ast/src/parser.rs:3449`, marked via `mark_config_const_runtime` at `crates/dsl_compiler/src/cg/lower/driver.rs:2208`, with generated public host mirror fields `pub <field>: <ty>` at `build_helper.rs:2270`). The runtime plumbing is ~70% built; only the *lowering* (runtime ConfigConst → buffer read, not baked const) and the *per-tick packing* (writing the mirrors into the cfg words) are missing.

**Decision:** implement the input channel by **completing the existing `@runtime` config path end-to-end** rather than adding a parallel `input {}` block. Same capability, less new surface, more general (it also advances the broader config-driven-sims gap). Everywhere the spec says `input.foo`, the implementation uses a `@runtime` config field `config.ctl.foo`.

## The field-name contract (defines parallelism)

All five plans agree on this `@runtime` config block, added to `vampire_survivors.sim` in **Plan 1** and frozen here so Plans 3 and 4 (the two ends of the channel) build against it in parallel without touching the same files:

```
config ctl {
  move_x:          f32 = 0.0 @runtime,   // player intent X, normalized [-1,1]
  move_y:          f32 = 0.0 @runtime,   // player intent Y, normalized [-1,1]
  move_level:      f32 = 0.0 @runtime,   // +speed per level (f32 math)
  bolt_level:      f32 = 0.0 @runtime,   // +bolt damage per level (f32 math)
  bolt_rate_level: u32 = 0   @runtime,   // -bolt period per level (u32 modulo)
  nova_level:      f32 = 0.0 @runtime,   // +nova damage/radius per level (f32 math)
  garlic_level:    f32 = 0.0 @runtime,   // 0.0 = inert; >0.0 enables garlic aura
  whip_level:      f32 = 0.0 @runtime,   // 0.0 = inert; >0.0 enables whip
}
```

**Type rule (avoids unverified `f32↔u32` casts):** fields feeding float arithmetic (damage, speed, `> 0.0` gates) are `f32`; only `bolt_rate_level` (an integer modulo divisor) is `u32`. Generated setters: `set_config_ctl_move_x(f32)` … `set_config_ctl_bolt_rate_level(u32)`.

Host setter (generated by Plan 1): `runtime.set_config_ctl_move_x(f32)` … (one per field; the generator already emits `pub move_x: f32` mirrors — Plan 1 adds the per-tick pack + confirms setters).

### One file touched by both Plan 1 and Plan 3: `assets/sim/vampire_survivors.sim`

Plan 1 **appends** the `config ctl {}` block (additive, top of file). Plan 3 **edits the rule bodies**. To keep these non-conflicting in the same wave they would race, so: **Plan 1 lands its `config ctl {}` append first** (it's in Wave 1), and Plan 3 (Wave 2) edits rules only. No overlap in practice — different regions, sequential waves.

## Execution waves (the parallelization plan)

```
Wave 1  (2 agents, fully parallel — zero shared files):
  ├── Plan 1: Runtime input channel        [dsl_compiler + build_helper + probe]
  └── Plan 2: engine_ui framework          [new crate]

Wave 2  (2 agents, parallel — share the field-name contract, not files):
  ├── Plan 3: Input-driven gameplay        [needs Plan 1]  edits vampire_survivors.sim rules + sims test
  └── Plan 4: Playable viewer HUD/menu/death [needs Plan 1 + 2]  edits viewer_runtime only
        → after both land: a short integration check (WASD moves the on-screen player).

Wave 3  (1 agent — must be last; shares files with 1, 3, 4):
  └── Plan 5: DSL ui {} block              [needs Plan 1, 3, 4]
```

**Merge-tax guard** (per the project's parallel-PR-merge-tax rule): Plan 1 and Plan 5 both extend DSL parser/codegen enums and `build_helper.rs`. They are placed in **different waves** (1 and 3) precisely so they never race on the same `match` arms / file regions. Plans 3 and 4 are parallel only because they own disjoint file sets and agree on the frozen field-name contract above.

## Shared Architectural Impact Statement (per-plan AIS specializes this)

- **Decision:** extend existing primitives — `@runtime` ConfigField path (Plan 1), `voxel_engine::EguiState` (Plans 2/4), the DSL parser/emitter (Plan 5). New crate `engine_ui` (Plan 2) because no reusable UI layer exists.
- **P1 (Compiler-First):** PASS — gameplay stays in `.sim`; input channel is sanctioned runtime I/O (like `sim_cfg.tick`); the `ui {}` block *extends* compiler-first by lowering UI to data.
- **P2 (Schema-Hash):** N/A — runtime-config fields live in the cfg uniform, not Agent SoA; no event/SoA layout change.
- **P3 (Parity):** PASS — runtime-config reads lower identically on both backends; host write is the determinism boundary.
- **P5 (Keyed PCG):** PASS — spawns + menu card-draw use `per_agent_u32`/seeded RNG.
- **P6 (Events):** PASS — input is read-only into rules.
- **P10 (No panic):** gated by each plan's headless runtime test.
- **P8:** each plan file carries its own filled AIS.
